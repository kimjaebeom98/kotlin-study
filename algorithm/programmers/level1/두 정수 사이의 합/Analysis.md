# 해설 — 두 정수 사이의 합

> [문제 원문](README.md) · [답안 코드](Solution.kt)

---

## 1. 문제 분석

주어진 건 정수 두 개, 구할 건 **그 사이 구간의 정수 합**(양 끝 포함). 제한 조건 세 줄이 사실상 이 문제의 전부다.

| 제한 조건 | 여기서 나오는 요구사항 |
|---|---|
| a와 b의 대소관계는 정해져있지 않다 | `a > b`인 경우를 따로 처리해야 한다 → **min/max 정규화** |
| a와 b가 같으면 아무 수나 리턴 | 정규화하면 `min == max`가 되어 자연히 그 수 하나가 나온다 → **분기 불필요** |
| ±10,000,000 범위의 정수 | 합의 최대 크기가 약 `5 × 10^13` → ⚠️ **`Int`로는 못 담는다** |

### ⚠️ 핵심 함정 — 반환 타입은 `Long`

합이 가장 커지는 경우는 `a = 0, b = 10,000,000`일 때다.

```
10,000,000 × 10,000,001 / 2 = 50,000,005,000,000  (약 5 × 10^13)
```

`Int`의 최대값은 `2,147,483,647`(약 2 × 10^9)이라 **네 자릿수쯤 모자란다.** 그래서 프로그래머스가 주는 시그니처도 반환 타입이 `Long`이다.

```kotlin
fun solution(a: Int, b: Int): Long
```

문제는 이게 **런타임 에러가 아니라 조용한 오답**으로 나타난다는 것. 예제 3개(`3~5`, `3~3`, `5~3`)는 값이 작아서 `Int`로도 전부 통과하기 때문에, 로컬 테스트만 보고 제출하면 채점에서만 틀린다.

## 2. 접근 — 등차수열 합 공식

`min`부터 `max`까지는 공차 1의 등차수열이므로, 반복 없이 O(1)로 구할 수 있다.

```
합 = (첫째항 + 마지막항) × 항의 개수 / 2
   = (min + max) × (max - min + 1) / 2
```

`(min + max) × (max - min + 1)`은 **항상 짝수**라 `/ 2`에서 정수 나눗셈 오차가 생기지 않는다. 둘 중 하나는 반드시 짝수이기 때문이다.

- 항의 개수 `(max - min + 1)`가 홀수면 → 양 끝의 홀짝이 같으므로 `(min + max)`가 짝수
- 항의 개수가 짝수면 → 그 자체가 짝수

### ⚠️ 공식을 써도 오버플로우는 남는다

`min`, `max`가 `Int`면 **곱셈이 `Int`로 계산된 뒤에** `Long`으로 변환된다. 반환 타입만 `Long`으로 바꿔도 중간 계산에서 이미 터진다.

```kotlin
// 🔍 실제 실행 결과 (min = 0, max = 10_000_000)
(min + max) * (max - min + 1) / 2            // → 143223616        ❌ 오버플로우
(min.toLong() + max) * (max - min + 1) / 2   // → 50000005000000   ✅
```

`min + max`(최대 2천만)와 `max - min + 1`(최대 2천만+1)은 각각 `Int` 범위 안이라 안전해 보이지만, **곱하는 순간** 약 `10^14`가 되어 넘친다.

#### 🔍 그래서 143223616은 어디서 나온 값인가

`Int`는 32비트다. 계산 결과가 32비트를 넘으면 JVM은 **에러를 내지 않고 넘친 상위 비트를 그냥 버린다**(two's complement 랩어라운드). 즉 결과가 `2^32`로 나눈 나머지가 된다.

```
     10,000,000 × 10,000,001 = 100,000,010,000,000     ← 참값
                                                          (32비트에 안 들어감)

     100,000,010,000,000 ÷ 4,294,967,296(=2^32) = 23283 … 286,447,232
                                                   ─┬───   ─────┬─────
                                       버려지는 상위 비트   남는 하위 32비트

     Int 곱셈 결과 = 286,447,232
     ÷ 2          = 143,223,616                      ← 우리가 본 값
```

참값 `100,000,010,000,000`에서 `2^32`의 배수만큼(`99,999,723,552,768`)이 통째로 사라지고, 나머지 `286,447,232`만 남는다. 여기에 `/ 2`가 적용돼 `143,223,616`이 된다.

⚠️ 이 값이 **양수**라는 게 특히 고약하다. 오버플로우라고 하면 보통 음수를 떠올리지만, 랩어라운드 결과는 남은 하위 32비트가 무엇이냐에 따라 양수일 수도 음수일 수도 있다. 부호가 멀쩡하니 "왜 값이 작지?" 하고 다른 데서 원인을 찾게 된다.

`/ 2`도 손상을 되돌리지 못한다. 나눗셈은 **이미 망가진 `286,447,232`**를 받을 뿐, 사라진 상위 비트를 복구할 방법이 없다.

그래서 **곱셈 이전에** 한쪽을 `Long`으로 올려야 한다. `min.toLong() + max`로 만들면 곱셈 자체가 64비트로 수행되어 `100,000,010,000,000`을 온전히 담는다. 반환할 때 `.toLong()`을 붙이는 건 이미 늦었다.

### 최종 코드

```kotlin
class Solution {
    fun solution(a: Int, b: Int): Long {
        val min = minOf(a, b)
        val max = maxOf(a, b)
        val count = max - min + 1
        return (min.toLong() + max) * count / 2
    }
}
```

`min.toLong() + max`에서 `Long + Int`는 `Long`으로 승격되므로, 이후 곱셈·나눗셈이 전부 64비트로 진행된다.

## 3. 다른 풀이

### 풀이 B — `LongRange.sum()`

```kotlin
fun solution(a: Int, b: Int): Long =
    (minOf(a, b).toLong()..maxOf(a, b).toLong()).sum()
```

가장 짧고 읽기 쉽다. 다만 O(n)이라 최악의 경우 **2천만 번 반복**한다. 이 문제 제한에서는 통과하지만 공식 풀이보다 느리다.

### 풀이 C — `sumOf`로 승격

```kotlin
fun solution(a: Int, b: Int): Long =
    (minOf(a, b)..maxOf(a, b)).sumOf { it.toLong() }
```

`IntRange`를 유지하면서 누적만 `Long`으로 받는 방식. 역시 O(n).

### ⚠️ `IntRange.sum()`은 쓰면 안 된다

```kotlin
(minOf(a, b)..maxOf(a, b)).sum()   // 반환 타입이 Int
```

`Iterable<Int>.sum()`의 반환 타입은 **`Int`**다. 누적 도중에 조용히 넘쳐서 엉뚱한 값이 나온다.

```
// 🔍 실제 실행 결과 (0..10_000_000)
(min..max).sum()                 → -2004260032      ❌ 음수가 되어버림
(min..max).sumOf { it.toLong() } → 50000005000000   ✅
(min.toLong()..max.toLong()).sum() → 50000005000000 ✅
```

⭐ **`sum()`은 원소 타입 그대로 누적한다.** 넓은 타입으로 받고 싶으면 `sumOf { it.toLong() }`처럼 **원소를 먼저 승격**시켜야 한다.

### ⚠️ 정규화를 빼먹으면 조용히 0

`a > b`일 때 `a..b`는 예외가 아니라 **빈 범위**다.

```
// 🔍 실제 실행 결과
(5..3).sumOf { it.toLong() }   → 0
```

입출력 예 3번(`a = 5, b = 3` → `12`)이 정확히 이걸 잡으려고 있는 케이스다. 빈 범위는 에러를 내지 않으므로 `0`이 그대로 정답인 척 리턴된다.

## 4. 복잡도

| 풀이 | 시간 | 공간 |
|---|---|---|
| A. 등차수열 공식 | **O(1)** | O(1) |
| B. `LongRange.sum()` | O(n), 최대 2 × 10^7 | O(1) |
| C. `sumOf { toLong() }` | O(n), 최대 2 × 10^7 | O(1) |

## 5. 정리

| | |
|---|---|
| ⭐ | 연속 정수 구간의 합은 `(첫항 + 끝항) × 개수 / 2`로 O(1) |
| ⭐ | `sum()`은 원소 타입으로 누적한다 — 넓히려면 `sumOf { it.toLong() }` |
| ⚠️ | 오버플로우는 **연산 시점**에 결정된다. 반환할 때 `.toLong()`은 이미 늦음 |
| ⚠️ | `a > b`인 범위는 예외가 아니라 빈 범위 → 조용한 `0` |
| ⚠️ | 오버플로우 결과가 꼭 음수인 건 아니다 — 양수로 나오면 더 못 알아챈다 |
| ⚠️ | 예제 케이스가 작으면 오버플로우 버그를 못 잡는다. 제한 조건의 **최대값으로 직접 테스트**할 것 |
